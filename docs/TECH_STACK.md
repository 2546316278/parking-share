| 项 | 实测值 | 说明 |

| Python | 3.9.24 | conda 环境 `yolov8_env` |
| GPU | RTX 4050 Laptop / CUDA 11.8 | 检测推理加速 |
| PyTorch | 2.6.0+cu118 | 已预装 |

**为什么复用 `yolov8_env` 而不新建环境**：该环境已装齐 torch(cu118)、ultralytics、opencv、paddleocr、flask、pymysql、redis、bcrypt，新建环境需重新下载数 GB 依赖且易出现 CUDA 版本错配。仅需补装 `APScheduler`、`PyJWT`。

**Python 3.9 的语法约束（重要）**：
- 不可使用 `X | Y` 联合类型注解（PEP 604，需 3.10+），统一用 `Optional[X]` / `Union[X, Y]`
- 不可使用 `match` 语句（需 3.10+）
- 可使用 `list[str]` 等内置泛型（PEP 585，3.9 起支持）

## 三、关键选型决策记录

### D1：检测与业务拆分为两个独立进程

- **决策**：`vision/` 为独立 Python 进程，负责读视频、跑检测、写状态到数据库；`server/` 为 Flask 应用，只读状态、不碰视频流。
- **理由**：旧项目把模型与 Web 塞进同一进程，导致模型加载阻塞启动、摄像头线程与请求线程争用同一模型实例（YOLO/PaddleOCR 均非线程安全）。拆分后检测服务崩溃不影响 Web 服务，且可独立重启。
- **代价**：需保证两边时钟与状态字段一致，用 `space_status_log` 表做唯一事实来源。

### D2：车位状态采用双字段设计，不可合并

- **决策**：`spaces` 表同时维护 `physical_status`（视觉写入：free/occupied）与 `business_status`（业务写入：available/reserved/in_use/maintenance）。
- **理由**：单一 status 无法表达"已被预约但实际被他人占用"这类冲突，而该冲突正是自动核销逻辑的处理对象，也是本系统的设计核心。
- **约束**：视觉进程只能写 `physical_status`，业务进程不能直接改 `physical_status`，反之亦然。跨状态的一致性问题由对账任务解决。

### D3：第一阶段不使用 Redis，用 MySQL 行锁保证预约不超卖

- **决策**：抢位使用 `SELECT ... FOR UPDATE` 配合 `(space_id, start_time, end_time)` 唯一约束；Redis 作为第二阶段的可选性能优化。
- **理由**：Redis 官方不支持 Windows，本地部署会增加约半天的环境成本；而"行锁 vs Redis 锁"的吞吐对比本身可作为论文的性能实验内容。
- **触发条件**：若并发压测显示行锁成为瓶颈，再引入 Redis 并保留原实现作为对照组。

### D4：支付采用模拟实现，但订单状态机按真实流程设计

- **决策**：不接入真实支付渠道，但订单状态完整实现 `pending → paid → in_use → completed` 及 `cancelled / refunded / violated`。
- **理由**：导师要求为"模拟支付下单"；完整状态机可支撑后续扩展，且状态流转本身是系统设计章节的内容。

### D5：车位检测采用"ROI 覆盖率 + 车辆唯一归属"判定

- **决策**：先标定车位多边形，每帧做车辆检测，计算车辆框落在车位多边形内的面积占比，超过阈值判为占用；同一辆车只归属覆盖率最高的车位。
- **理由**：相较训练车位分类模型，该方案不需为每个车位准备样本，冷启动成本低，且可解释性强（能输出覆盖率数值用于调试与答辩演示）。
- **补充**：PKLot 数据集上的分类模型作为**对比实验**保留在 `experiments/`，用于论文的算法对比章节，不进入主链路。

## 五、明确不采用的技术

| 技术 | 原因 |
|---|---|
| Q-Learning 自适应参数 | 属旧项目内容，与本选题无关，纳入会分散答辩焦点 |
| 讯飞人脸登录 | 面向公众用户的共享平台无此需求，且涉及人脸数据合规问题 |
| NL→SQL 智能助手（Ollama） | 存在 SQL 注入面，且与选题无关 |
| 原生 HTML 多页 + 全局函数 | 页面数量增加后维护成本陡增，改用 Vue 3 组件化 |
| `setInterval` 轮询 base64 帧 | 带宽与 CPU 浪费严重，改用 MJPEG 流或前端直接拉取快照 |
| Redis 分布式锁（第一阶段） | 见 D3 |
